# 09-面试用项目关键笔记

日期：2026-06-11

## 项目一句话

基于 Ubuntu 24.04、ROS2 Jazzy、Gazebo Harmonic 和 Navigation2，从 0 搭建并实现了一个移动机器人仿真与导航学习项目，覆盖 ROS2 通信、服务参数、URDF/Gazebo 仿真、TurtleBot3、SLAM、Nav2 bringup 和 C++ action 客户端。

## 面试开场版本

### 30 秒版本

我做了一个 ROS2 移动机器人仿真导航项目。环境是 WSL2 Ubuntu 24.04 + ROS2 Jazzy，仿真用 Gazebo Harmonic。项目分两条主线：第一条是从 0 实现两轮差速机器人，包括 URDF、Gazebo 插件、ROS-GZ 桥接、键盘遥控、控制器、服务切换模式和参数化控制；第二条是基于 TurtleBot3 和 Navigation2，跑通 Gazebo、SLAM、Nav2 lifecycle，并写了 C++ `NavigateToPose` action 客户端。整个过程用 GitHub 做 `feature -> dev -> main` 版本管理。

### 1 分钟版本

项目的目标不是只跑一个 demo，而是把 ROS2 移动机器人开发链路拆开学透。我先搭建 ROS2 Jazzy 和 Gazebo Harmonic 环境，然后实现 `differential_drive_robot` 包：通过 `teleop_keyboard` 发布 `/teleop_cmd`，`robot_controller` 订阅后做限速、安全检查和模式控制，再发布 `/cmd_vel`，经 `ros_gz_bridge` 驱动 Gazebo 中的差速机器人，最后通过 `/odom`、`/joint_states`、`/tf` 验证闭环。之后我把控制方式升级成 service + parameter，支持 `/set_control_mode` 和运行时调参。最后实现 `nav2_cpp_tutorial`，用 launch 一键启动 TurtleBot3 Gazebo、SLAM 和 Nav2，并通过 C++ action client 对接 `/navigate_to_pose`。

### 3 分钟版本

这个项目我按真实机器人软件的分层思路来设计：底层是仿真模型和桥接，中间是 ROS2 控制节点，上层是导航框架和应用客户端。

底层我用 URDF 描述机器人结构，在 Gazebo Harmonic 里加载 `gz-sim-diff-drive-system` 和 joint state 插件，通过 ROS-GZ bridge 把 Gazebo 的 `/odom`、`/joint_states`、`/tf` 桥到 ROS2，把 ROS2 的 `/cmd_vel` 桥回 Gazebo。这样仿真和 ROS 节点解耦，后续替换真实底盘时接口也比较清晰。

中间层我写了 `robot_controller` 和 `teleop_keyboard`。键盘节点负责发布遥控命令和模式，控制器负责统一处理手动、自动直行、圆形运动、避障、墙跟随等模式。这里我故意用了 topic、service、parameter 三种机制：速度和传感器用 topic，因为是连续异步数据；模式切换用 service，因为需要明确成功或失败；速度上限、安全距离、控制频率用 parameter，因为这些应该运行时可调。

上层我没有自己重写完整导航栈，而是接入 Navigation2。Nav2 适合真实项目，因为它已经提供 BT Navigator、Planner Server、Controller Server、Costmap、Recovery/Behavior、Lifecycle 管理。我写了一个 C++ `Nav2Client`，通过 `nav2_msgs/action/NavigateToPose` 发送导航目标，处理 feedback、result、cancel 和状态发布。这个选择也体现了我对 ROS2 action 的理解：导航任务是长耗时任务，需要反馈、取消和最终结果，不适合用 service 或普通 topic。

## 主要模块设计和原因

### 1. `differential_drive_robot`

定位：从 0 实现的差速机器人仿真控制包。

核心文件：

```text
ros2-src/differential_drive_robot
|-- urdf/robot_harmonic.urdf
|-- worlds/empty_world.sdf
|-- config/bridge.yaml
|-- config/controller_params.yaml
|-- launch/gazebo_harmonic.launch.py
|-- src/robot_controller.cpp
|-- src/teleop_keyboard.cpp
`-- srv/SetControlMode.srv
```

设计原因：

- 用 URDF 描述机器人结构，便于接入 `robot_state_publisher` 和 TF。
- 使用 `base_footprint -> base_link`，避免 root link 带惯性导致 KDL warning。
- 用 Gazebo Harmonic 插件实现差速运动和 joint state，少写底层物理逻辑。
- 用 ROS-GZ bridge 连接 ROS2 和 Gazebo，保持仿真侧和 ROS 侧解耦。
- `/cmd_vel` 使用 `TwistStamped`，适配 Jazzy/Harmonic 当前接口。
- 控制器集中做限速、速度平滑、安全检查和模式切换，避免多个节点同时抢控制权。

### 2. `robot_controller`

职责：

- 订阅 `/teleop_cmd`。
- 订阅 `/control_mode`。
- 提供 `/set_control_mode` 服务。
- 订阅 `/odom`、`/joint_states`、`/scan`。
- 发布 `/cmd_vel`。
- 支持参数动态更新。

为什么这样设计：

- 手动遥控和自动控制都收敛到同一个控制器，便于统一限速和安全策略。
- service 用于模式切换，因为它需要返回 `success/message`。
- parameter 用于速度、加速度、安全距离和控制频率，因为这些值需要调试时动态修改。
- 控制 loop 按固定频率运行，输出速度平滑，不让速度突变。

### 3. `teleop_keyboard`

职责：

- 把键盘输入转换成 `/teleop_cmd`。
- 用数字键发布 `/control_mode`。

为什么这样设计：

- 遥控节点只负责输入，不直接碰 Gazebo。
- 控制策略由 `robot_controller` 统一处理，职责更清晰。

### 4. `nav2_cpp_tutorial`

定位：Navigation2 C++ action 客户端和 bringup 学习包。

核心文件：

```text
ros2-src/nav2_cpp_tutorial
|-- include/nav2_cpp_tutorial/nav2_client.hpp
|-- src/nav2_client.cpp
|-- src/nav2_simple_test.cpp
|-- config/nav2_params.yaml
`-- launch/nav2_cpp_demo.launch.py
```

设计原因：

- Nav2 已经是 ROS2 官方导航框架，不重复造完整导航栈。
- C++ action client 用于学习真实工程中如何和 Nav2 交互。
- launch 文件统一启动 TurtleBot3 Gazebo、SLAM、Nav2，降低复现成本。
- 参数文件显式配置 planner、controller、costmap、behavior、velocity smoother、collision monitor、docking server，解决 Jazzy bringup 默认节点变多的问题。

### 5. GitHub 分支流

当前项目使用：

```text
feature/<功能名> -> dev -> main
```

设计原因：

- `feature/*` 记录单次功能或文档迭代。
- `dev` 做集成。
- `main` 保持稳定可展示版本。
- 面试时可以说明自己不是只写代码，也有基本版本管理意识。

## 涉及的关键技能和知识点

### ROS2 基础通信

- Topic：连续异步数据流，如 `/cmd_vel`、`/odom`、`/scan`、`/tf`。
- Service：一次请求一次响应，如 `/set_control_mode`。
- Action：长时间任务，如 Nav2 的 `/navigate_to_pose`。
- Parameter：运行时可调配置，如速度上限、安全距离、控制频率。

面试可强调：

```text
我不是机械地使用通信机制，而是根据数据语义选择：
高频连续数据用 topic，离散命令用 service，长耗时导航任务用 action，可调配置用 parameter。
```

面试常问回答：


## 面试常见追问

### Q1：为什么速度控制用 topic，不用 service？

速度命令是连续、高频、实时性较强的数据流。Topic 更适合发布订阅模型，控制器持续接收最新速度即可。Service 是请求响应模型，如果用 service 发送速度，会引入阻塞和响应等待，不适合高频控制。

### Q2：为什么导航目标用 action？

导航是长时间任务，发送目标后机器人可能需要规划、避障、恢复、取消、重试。Action 支持 goal、feedback、result 和 cancel，能持续反馈剩余距离、恢复次数和最终状态，语义上比 service 和 topic 更合适。

### Q3：为什么要有 `base_footprint`？

`base_footprint` 表示机器人在地面的二维投影，适合移动机器人导航和局部规划。`base_link` 可以表示机器人本体三维中心。把 `base_footprint` 作为根 link，还能避免 root link 带惯性导致的 KDL warning。

### Q4：Nav2 lifecycle active 说明什么？

说明 Nav2 的 lifecycle nodes 已经完成 configure 和 activate，action server、planner、controller、costmap 等组件已经进入可工作状态。如果某个节点参数缺失，比如 `collision_monitor` 或 `docking_server`，lifecycle 会在 bringup 阶段失败。

### Q5：项目中遇到的最典型问题是什么？

Jazzy 版本和教程资料不完全一致。比如 Nav2 插件类名要用 `::`，DWB controller 需要 critics，Jazzy bringup 默认启动 `collision_monitor` 和 `docking_server`，缺参数会导致 lifecycle 失败。我通过查官方已安装参数文件、补齐配置、反复冒烟测试解决。

### Q6：这个项目和课程源码相比有什么不同？

我的项目更偏“跑通现代 ROS2 工程链路”：Jazzy/Harmonic、ROS-GZ、Nav2 bringup、action client 和版本管理。课程 `turtle_bot3` 更偏“自研导航算法教学”：传感器处理、A* 路径规划、路径跟随。后续我会把这部分作为下一阶段补充。
